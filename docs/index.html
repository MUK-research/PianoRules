MUSICAL GRAMMAR

PianoRules

A small language for defining relationships between a performer and a MIDI-capable piano. Write when something should happen, then write what the instrument should do.

Open PianoRules Shared file library Markdown version

The basic idea

trigger:
  action

A trigger can be a note, a chord, a dynamic range, a point in time, a random timer, a held key, or another sequence that is currently playing. Actions can produce notes, intervals relative to what you played, chords, repetitions, named sequences, MIDI files, and sound files.

Edit the rules in the browser, then press Apply changes or ⌘/Ctrl+Enter. The new musical logic becomes active immediately.

Event triggers: when

Any note

when any note:
  play +12

Every played note can become the beginning of a relationship.

Specific note

when note C4:
  play G4

Use note names or MIDI numbers.

Dynamics

when any note velocity 90..127:
  play -12 velocity 45

Different dynamic regions can open different behaviours.

Chord

when chord [C4 E4 G4] within 180ms:
  play [D5 F#5 A5]

A sonority can act like a harmonic password.

State triggers: while

when reacts to an event. while remains active for as long as a musical state is true.

While a key is held

while note C4 down every 180ms:
  play +7 velocity input*0.6 for 80ms

Hold C4 and the process continues. Release C4 and future events belonging to that while-rule stop.

While any key is held

while any note down velocity 80..127 every 120ms:
  play +12 velocity input*0.45 for 60ms

This turns the physical act of holding the keyboard into a gate for a generative process.

While another sequence is playing

sequence answer:
  play +12 for 130ms
  wait 160ms
  play +7 for 130ms
  wait 160ms
  play +3 for 180ms

when note D4:
  play sequence answer

while sequence answer playing every 220ms:
  play -12 velocity 35 for 80ms

The second process exists only during the lifetime of answer. Its relative actions inherit the musical context that launched that sequence.

A sequence's lifetime is calculated from its waits, note durations, repetitions and nested PianoRules sequences. If a sequence contains an audio or MIDI file and you want a precise longer state, add explicit wait time to define that timeline.

Time triggers

After the beginning

after start 8s:
  play [C3 G3 C4] velocity 48 for 700ms

Regular pulse

every 3s:
  play C5 velocity 40 for 100ms

Random autonomous timing

every random 2s..5s:
  play random [C4 D4 E4 G4 A4] velocity 25..55 for 140ms

These rules let the instrument have temporal behaviour that is not directly controlled by the pianist.

Sections and musical form

A piece can contain several independent sections. Only one section is active at a time, and the first section in the file is active by default.

section Opening:
  when any note:
    play +7 velocity input*0.5

  when note C7:
    go to section Echoes

section Echoes:
  every random 2s..5s:
    play random [C4 E4 G4 B4] velocity 25..50

  when note C1:
    go to section Opening

A section change can itself be the action produced by a note, chord, dynamic condition, timer, held-note process, or sequence.

Changing section is a reset: the old section's timers, repetitions, sequences and while processes are cancelled; PianoRules sends all-notes-off / all-sound-off, stops audio it started, resets the local section clock, and activates only the new section's code.

The active section is shown beside the editor title, and that section's code is visually emphasized in the code window. Notes that were already held before a section change do not automatically start a new held-note process in the new section.

Indentation after section is optional

The section header already establishes the structural level, so both styles are valid:

section Opening:
  when any note:
    play +7
section Opening:
when any note:
  play +7

Actions still need to be indented beneath the trigger or sequence they belong to.

Click a section to rehearse it

Click anywhere inside an inactive section's code in the editor to activate that section immediately. If the editor contains unapplied changes, PianoRules applies the current script first and then enters the clicked section.

Open form rather than a fixed chain

Sections do not have to follow one another sequentially. They can loop, branch, return, or be selected by the performer. This makes them useful for improvisational navigation, game-like forms, open scores, and pieces in which the piano itself helps determine the next formal state.

A file without any section ...: headings still works and is treated as one implicit section called Main.

Named sequences

Sequences are reusable musical objects: motives, responses, textures, cadences, interruptions, or algorithmic characters.

sequence answer:
  play +12 velocity input*0.8 for 130ms
  wait 160ms
  play +7 velocity input*0.7 for 130ms
  wait 160ms
  play +3 velocity input*0.6 for 180ms

when note D4:
  play sequence answer

wait advances the local timeline. Without a wait, several actions can begin from the same point in time.

MIDI and sound files

when note F4:
  play midi "gesture.mid"

when note G4:
  play sound "resonance.wav"

Local assets

Drag files onto the asset area at the bottom of PianoRules. They are stored locally in that browser, so you can use the filename in your rules on later visits.

Remote asset folder

Declare a global folder near the beginning of a rules file:

assets from "./assets/"

Relative filenames used by play midi and play sound are resolved against that folder. An absolute web folder is also valid:

assets from "https://example.org/my-piece-assets/"
Preloading: whenever you press Run rules or Apply changes, PianoRules scans the complete piece and downloads every referenced remote asset before starting the engine. If an asset cannot be prepared, the rules remain stopped and the problem is shown in the diagnostics.

One-off remote files

asset "special.wav" from "https://example.org/files/special.wav"

when note A4:
  play sound "special.wav"

This keeps the musical action readable even when one file lives somewhere else.

Then use assets from "./assets/". Same-origin static assets are the simplest and most dependable performance setup.

Shared library: open the communal Google Drive folder, download an interesting asset, then either drag it into PianoRules or copy it into your repository's assets/ folder. A Google Drive folder is useful as a library/distribution space, but not as a raw filename-addressable runtime folder; Drive download endpoints are not reliably fetchable from browser JavaScript because of cross-origin restrictions.

Share a piece with one URL

A complete work can live in the PianoRules Library, in its own GitHub repository, or as a public .rules file elsewhere. The ruleset URL parameter tells PianoRules which piece to open.

Built-in Library

Library/
  Cage/
    Cage.rules
    assets/
      sound.wav
      gesture.mid
https://YOUR-PAGES-URL/?ruleset=Cage

The short name resolves to Library/Cage/Cage.rules. Without an explicit assets from ... declaration, Library/Cage/assets/ is used automatically.

Another GitHub repository

Rule-Gamelan/
  Gamelan.rules
  assets/
    gong.wav
    interlock.mid
?ruleset=https%3A%2F%2Fgithub.com%2FAdrianArtacho%2FRule-Gamelan

PianoRules interprets Rule-Gamelan as the piece Gamelan and looks for Gamelan.rules in main, then master. A repository named simply Gamelan follows the same convention. Exact GitHub blob/.../*.rules links are accepted too.

Direct file elsewhere

?ruleset=https%3A%2F%2Fexample.org%2Fpieces%2FClouds%2FClouds.rules

Other hosts should provide a direct public .rules URL and permit browser/CORS access. Relative asset declarations are resolved from the score's own directory.

Self-contained works: when a score is loaded through ruleset and it has no assets from ... declaration, PianoRules automatically looks in an assets/ folder beside the .rules file. The complete piece can therefore travel as one repository or folder.

The remote repository supplies only PianoRules text and media. It cannot inject JavaScript into the application; the loaded text still passes through the normal PianoRules parser before it can run.

Things to explore

A delayed shadow

when any note:
  play +12 velocity input*0.5 after 400ms

A held-key machine

while any note down every 160ms:
  play +7 velocity input*0.4 for 70ms

Dynamic bifurcation

when any note velocity 1..60:
  play +12 velocity 25 after 500ms

when any note velocity 90..127:
  play -12 velocity input*0.8 repeat 5 every 120ms

A harmonic password

when chord [C4 E4 G4] within 160ms:
  play sequence answer

An autonomous partner

every random 3s..9s:
  play random [C3 D3 F3 G3 A3] velocity 20..45 for 180ms

The richest use of PianoRules is often not “automatic accompaniment” but musical causality: a note casts a shadow, a chord opens a process, a held key sustains a machine, dynamics switch behaviours, and one process awakens another.

Credits

PianoRules was created by Adrián Artacho, composer and educator at the Music and Arts University of the City of Vienna (MUK).

The project is conceived as an open environment for performer–algorithm interaction, experimentation, teaching, and shared musical materials.

The aim is not to make the performer write conventional software. It is to make musical relationships explicit, editable and playable.
